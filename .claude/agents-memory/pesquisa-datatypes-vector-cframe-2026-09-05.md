## 1. Construtores

### Vector3 — fonte: `Vector3.yaml`
- `Vector3.new(x: number?, y: number?, z: number?): Vector3` — todos os 3 parâmetros com default `0`. `Vector3.new()` é válido (retorna `(0,0,0)`).
- `Vector3.FromNormalId(normal: Enum.NormalId): Vector3` — vetor unitário. Ex.: `Enum.NormalId.Top → (0,1,0)`, `Enum.NormalId.Front → (0,0,-1)`.
- `Vector3.FromAxis(axis: Enum.Axis): Vector3` — vetor unitário. `Enum.Axis.X → (1,0,0)`, `.Y → (0,1,0)`, `.Z → (0,0,1)`.
- Não existe `Vector3.FromAxis`/`FromNormalId` com overload adicional. Não há mais construtores estáticos documentados.

### Vector2 — fonte: `Vector2.yaml`
- `Vector2.new(x: number?, y: number?): Vector2` — ambos default `0`.
- **Não existem `Vector2.FromNormalId`/`FromAxis`** no YAML — não confundir com Vector3.

### CFrame — fonte: `CFrame.yaml` (todos os overloads abaixo vêm de entradas separadas em `constructors:`, cada uma com seu próprio `summary`/`description`)
Overloads de `CFrame.new` confirmados, na ordem em que aparecem no YAML oficial:
1. `CFrame.new()` — identidade, posição `(0,0,0)`, equivalente a `CFrame.identity`.
2. `CFrame.new(pos: Vector3)` — sem rotação.
3. `CFrame.new(pos: Vector3, lookAt: Vector3)` — posição em `pos`, olhando para `lookAt`, assumindo `(0,1,0)` como "up". **Documentado como legado**: "This constructor overload has been replaced by `CFrame.lookAt()`... At high pitch angles (~82°) you may experience numerical instability."
4. `CFrame.new(x: number, y: number, z: number)` — 3 args, sem rotação. Equivalente a `CFrame.new(Vector3.new(x,y,z))`.
5. `CFrame.new(x, y, z, qX, qY, qZ, qW: number)` — 7 args, posição + quatérnion. **Quatérnion não-unitário é normalizado automaticamente** ("If this isn't the case, the quaternion will be normalized").
6. `CFrame.new(x, y, z, R00, R01, R02, R10, R11, R12, R20, R21, R22: number)` — 12 args, posição + matriz de rotação 3×3 **linha-major** (`[[R00 R01 R02][R10 R11 R12][R20 R21 R22]]`). Confirma a ordem exata dos 12 componentes — mesma ordem que `GetComponents()` retorna.

**Não existem overloads de 1 ou 2 argumentos além dos listados** (não há `CFrame.new(number)` sozinho, por exemplo). O overload de 0 args é distinto do de 1 arg (Vector3) e do de 3 args (x,y,z) — são 3 entradas de `constructors:` separadas no YAML.

Outros construtores estáticos de CFrame (todos confirmados em `constructors:`):
- `CFrame.lookAt(at: Vector3, lookAt: Vector3, up: Vector3? = Vector3.yAxis): CFrame`
- `CFrame.lookAlong(at: Vector3, direction: Vector3, up: Vector3? = Vector3.yAxis): CFrame` — "equivalente a `CFrame.lookAt(at, at + direction)`". **Confirmado que existe** (o prompt perguntava "se existir" — existe).
- `CFrame.fromRotationBetweenVectors(from: Vector3, to: Vector3): CFrame` — não estava na lista do pedido, mas existe; posição sempre `(0,0,0)`.
- `CFrame.fromEulerAngles(rx, ry, rz: number, order: Enum.RotationOrder? = Enum.RotationOrder.XYZ): CFrame` — versão genérica com ordem parametrizável (também não estava na lista pedida, mas existe e é a "moderna").
- `CFrame.fromEulerAnglesXYZ(rx, ry, rz: number): CFrame`
- `CFrame.fromEulerAnglesYXZ(rx, ry, rz: number): CFrame`
- `CFrame.Angles(rx, ry, rz: number): CFrame` — **"Equivalent to `fromEulerAnglesXYZ()`"** (literal, é alias).
- `CFrame.fromOrientation(rx, ry, rz: number): CFrame` — **"Equivalent to `fromEulerAnglesYXZ()`"** (literal, é alias — cuidado, o nome sugere Euler genérico mas é especificamente YXZ).
- `CFrame.fromAxisAngle(v: Vector3, r: number): CFrame` — eixo normalizado internamente, posição sempre `(0,0,0)`, regra da mão direita.
- `CFrame.fromMatrix(pos: Vector3, vX: Vector3, vY: Vector3, vZ: Vector3?): CFrame` — **`vZ` é opcional**; se omitido, `vZ = vX:Cross(vY).Unit`. `vX`≡RightVector, `vY`≡UpVector, `vZ`≡`-LookVector`.

**Incerto/fora do YAML**: assinaturas de parâmetro individuais não trazem tipo de retorno explícito no schema YAML (o schema separa `parameters` de um campo de retorno que não aparece nos `constructors` — só nos `methods`). O tipo de retorno "CFrame" para todo constructor é inferido do nome da classe pai do YAML (`name: CFrame`), não de um campo explícito — comportamento consistente e sem ambiguidade, mas registro para quem gerar tipos automaticamente.

Ver seção 9 e "Incerto".

### Unário `-v` (negação)
**Não há seção de operadores unários em nenhum dos 3 YAMLs** (`math_operations` só lista pares binários). Não há nenhum exemplo com `-cframe` (CFrame não deveria suportar unário, dado que nem `+`/`-` entre dois CFrames é suportado).

## 6. `tostring()` — formato exato

**Não há especificação formal em nenhum YAML** (não existe campo `tostring_format` no schema). A evidência vem de **exemplos de código embutidos na prosa oficial** (`description`/`summary` dos próprios YAMLs), que são gerados/revisados pela mesma pipeline oficial — tratando como fonte primária, mas note que são exemplos ilustrativos, não uma especificação formal de formatação.

### Formato geral confirmado por múltiplos exemplos idênticos nos 3 tipos
Separador: **vírgula + espaço** (`", "`), sem parênteses/colchetes, um valor por componente, na ordem X,Y[,Z].

- Vector2: `print(Vector2.zero) --> 0, 0` · `print(Vector2.new(1,2) + Vector2.new(3,4)) --> 4, 6`
- Vector3: `print(Vector3.zero) --> 0, 0, 0` · `print(a:Cross(b)) --> 0, 0, 1` · `print(v.Unit) --> 0.6, 0.8, 0`
- CFrame: `print(cf:PointToWorldSpace()) --> 5, 10, 0` (Vector3-shaped, 3 valores) e `print(cf:ToWorldSpace(offset)) --> 5, 12, 0, 1, 0, 0, 0, 1, 0, 0, 0, 1` (CFrame-shaped, **12 valores, mesma ordem de `GetComponents()`**: x,y,z,R00,R01,R02,R10,R11,R12,R20,R21,R22).

**Confirmado**: `tostring(CFrame)` produz os 12 componentes na mesma ordem que `GetComponents()`, separados por `", "` — não trunca a matriz de rotação mesmo quando é a identidade.

### Formatação numérica de cada componente — fonte secundária (DevForum), não a doc de referência
A doc de referência só usa números "bonitos" nos exemplos (`0`, `1`, `0.6`), o que não prova quantas casas decimais aparecem em números "feios". Um exemplo real de usuário no DevForum (thread "Limiting Precision Issues With Vector3", `https://devforum.roblox.com/t/limiting-precision-issues-with-vector3/2306131`) mostra:
```
worldPosition = Vector3.new(-8.9, 0, -1.3)
print(worldPosition) --> -8.899999618530273, 0, -1.2999999523162842
```
Isso indica que **cada componente é formatado com a representação decimal completa do double resultante do widening do float32 armazenado** (não há arredondamento/truncamento de casas decimais no tostring) — o formato não é "compacto com N casas fixas", é o número double "cru". **Isso é evidência de fórum (comunidade), não uma citação da doc oficial** — tratar como alta confiança mas não 100% oficial. Recomendação prática para `coder-runtime`: implementar `__tostring` chamando o `tostring()` nativo do Lune em cada componente (double) já narrowed/widened para float32, e juntar com `", "` — isso reproduz o comportamemto observado sem precisar reimplementar um formatador customizado.

**Incerto**: não encontrei o algoritmo exato de conversão double→string que o Luau/Roblox usa internamente (quantidade de dígitos significativos, se é "shortest round-trip" tipo Grisu/Ryu ou `%.14g` clássico do Lua 5.1). Isso não bloqueia a implementação (ver recomendação acima), mas fica marcado como não confirmado por fonte primária.

## 7. `typeof()` e `type()`

Fonte primária de `typeof()`: `content/en-us/reference/engine/globals/RobloxGlobals.yaml` — descrição oficial: **"Returns the type of the object specified, as a string. This function is more accurate than Luau's native `type` function, as it does not denote Roblox-specific types as `userdata`."**

| Tipo | `typeof(x)` | `type(x)` |
|---|---|---|
| `Vector3.new()` | `"Vector3"` | **`"vector"`** (não `"userdata"`) |
| `Vector2.new()` | `"Vector2"` | `"userdata"` |
| `CFrame.new()` | `"CFrame"` | `"userdata"` |

**Achado importante, contraria a suposição do pedido original**: `type(Vector3.new())` **NÃO retorna `"userdata"`** na Roblox atual — retorna `"vector"`. Isso é resultado de uma migração de engine em que `Vector3` passou a ser implementado sobre o **tipo primitivo nativo `vector` da própria linguagem Luau** (não mais um userdata alocado no heap). `Vector2` e `CFrame` **não foram migrados** e continuam `"userdata"` — fonte: anúncio oficial da equipe Roblox no DevForum, thread "Native Luau Vector3 Beta" (`https://devforum.roblox.com/t/native-luau-vector3-beta/1180548`) e o anúncio de mudança de comportamento "Behavior change: type() will start returning 'vector' for Vector3" (`https://devforum.roblox.com/t/behavior-change-type-will-start-returning-vector-for-vector3/1217482`). Ambos os threads afirmam explicitamente que **Vector2 e CFrame usarão "estratégia de implementação diferente"** para otimizações futuras — ou seja, a divergência Vector3-vs-{Vector2,CFrame} é intencional e permanente, não uma fase transitória.

Confirmado também pelo mesmo anúncio: `typeof()` continua retornando `"Vector3"` sem mudança — só `type()` muda.

**Incerto / ressalva sobre a data exata**: os dois fetches da thread do DevForum retornaram datas de rollout conflitantes/possivelmente mal extraídas pela ferramenta de fetch (`"April 21, 2021"` para o post e `"June 10/14, 2021"` para o rollout Studio/live) — essas datas parecem cedo demais para uma mudança dessa magnitude e podem estar erradas (extração automática de página, não uma citação literal confiável de metadado). **O fato em si (type() retorna "vector" para Vector3 hoje, na versão atual do Roblox) está confirmado com alta confiança por dois anúncios independentes da própria equipe Roblox — a data exata do rollout NÃO está confirmada e não deveria ser citada como precisa.**

**Fonte da linguagem** (`luau.org/library`, oficial): o tipo `vector` é primitivo da VM Luau (não Roblox-specific), com 3 componentes por padrão (`x`,`y`,`z`; 4º componente `w` só se `LUA_VECTOR_SIZE=4`, que não é o caso do runtime do Roblox/Lune por padrão), imutável (sem escrita em componente individual), com biblioteca `vector.*` (`vector.create`, `vector.magnitude`, `vector.normalize`, `vector.cross`, `vector.dot`, `vector.angle`, `vector.floor`, `vector.ceil`, `vector.abs`, `vector.sign`, `vector.clamp`).

**Implicação de design para `coder-runtime`/`arquiteto`**: como o Lune roda sobre a mesma VM Luau, ele **já tem o tipo nativo `vector`** disponível (biblioteca `vector.*` e literal `type(x) == "vector"`) — não precisa ser userdata/tabela costurada à mão para bater com o comportamento real do `type()`. Isso é uma decisão de arquitetura relevante: dá para implementar `Vector3` simulado usando o `vector` nativo do Luau para fidelidade total de `type()`, enquanto `Vector2`/`CFrame` precisam ser tabelas com metatable (userdata simulado) porque são `"userdata"` de verdade. **Não confirmado neste momento se o Lune expõe a biblioteca `vector.*`/o tipo nativo com `LUA_VECTOR_SIZE=3` habilitado por padrão** — isso é uma pergunta de pesquisa separada sobre o runtime Lune (fora do escopo deste relatório, que é sobre a API do datatype, não sobre o Lune) e deveria ser confirmada antes do `arquiteto` decidir usar o `vector` nativo.

## 8. Precisão numérica (float32 vs double)

Múltiplas fontes convergentes, nenhuma delas 100% "isso é a especificação formal do datatype", mas a convergência é forte:

1. **`content/en-us/luau/numbers.md`** (oficial, creator-docs): define a classificação `float` usada na doc de referência como "[single-precision (32-bit) floating-point]... sufficiently precise for most use cases and requires less memory". Isso é a Roblox dizendo que existe uma categoria `float` (32-bit) distinta de `number`/`double` (64-bit) **usada na API reference para ser mais específica sobre como usar cada API** — ou seja, quando uma propriedade é documentada/tageada como `float` na doc de referência, ela é 32-bit internamente no engine, mesmo passando por Luau (que só tem `number` = double).
2. **`Full-API-Dump.json` local** confirma que essa distinção `float` vs `number`(double) existe de fato como campo `ValueType.Name` em propriedades de Class (ex.: `AnimationTrack.Speed` é `float`, `AnimationTrack.TimePosition` é `float`) — MAS **as propriedades `BasePart.Position`/`.Size`/`.Orientation`/`.CFrame` aparecem no dump com `ValueType: {Category: "DataType", Name: "Vector3"|"CFrame"}`, opacas — o dump de classes NÃO decompõe Vector3/CFrame em float/double internamente.** Ou seja: o dump não prova diretamente que os componentes X/Y/Z de Vector3 são float32 — só prova que a distinção float/double existe em outro lugar do mesmo sistema de tipos.
3. **`luau.org/library`** (oficial, sobre a linguagem): o tipo primitivo `vector` da Luau usa componentes de **32 bits** internamente (evidenciado pela API em C, `lua_pushvector`, que recebe `float`, não `double`).
4. **DevForum**: Vector3 hoje É implementado usando esse tipo nativo `vector` da Luau (ver seção 7) → portanto os componentes de `Vector3` são float32 por transitividade (2+3+4 juntos).
5. **`dom.rojo.space/binary.html`** (rbx-dom, ecossistema Rojo): o formato binário `.rbxm`/`.rbxl` real documenta explicitamente: **"The `Vector3` type is a struct composed of three `Float32` values"** (12 bytes/Vector3) e **"The `Vector2` type is a struct composed of two `Float32` values"** (8 bytes/Vector2), e para CFrame: **"the `Orientation` field is stored as nine untransformed IEEE-754 standard 32-bit floats"** (a matriz de rotação 3×3). **Ressalva**: isso documenta o formato de **arquivo serializado**, não necessariamente a representação em memória durante a execução — mas é extremamente improvável que o engine converta para double em runtime e depois volte a comprimir para float32 só para salvar; a leitura natural é que a representação em memória já é float32 e o arquivo só espelha isso.

### Conclusão sobre precisão (alta confiança, mas nem toda peça é uma citação direta e única)
- **Vector3, Vector2 e CFrame armazenam seus componentes numéricos como float32 (single-precision) no Roblox real** — confirmado por convergência de 5 fontes (linguagem Luau + formato de arquivo + comportamento documentado do `type()`), nenhuma delas uma frase única "Vector3.X é float32" na doc de referência do datatype em si (que só diz `type: number` para X/Y/Z, sem qualificar a precisão).
- **Efeito observável confirmado por exemplo real** (DevForum, não teste próprio): `Vector3.new(-8.9, 0, -1.3)` impresso mostra `-8.899999618530273, 0, -1.2999999523162842` — ou seja, o valor exibido já reflete o arredondamento para float32 (widened de volta para double só para exibição/aritmética Luau).
- Por extensão lógica (não testada e não citada diretamente): `Vector3.new(0.1, 0, 0).X == 0.1` deveria ser **`false`** no Roblox real, porque `0.1` como literal double é distinto de `0.1` narrowed para float32 e widened de volta. **Não encontrei um exemplo citável específico com `0.1` — é inferência direta a partir do padrão confirmado com `-8.9`, tratar como quase certo mas não 100% citado literalmente.**

### Decisão que isso implica para o LuauBench
Se o objetivo é fidelidade com o Roblox real (Regra 00 do projeto), o `coder-runtime` **precisa truncar/arredondar para float32 na construção/atribuição** dos componentes de Vector3/Vector2/CFrame (ex.: usando alguma rotina de narrowing float64→float32→float64, já que Luau só tem double nativamente para armazenamento genérico — a menos que use o tipo `vector` nativo da própria Luau, que já faz isso automaticamente, ver seção 7). Usar double puro sem essa perda de precisão é uma **divergência deliberada e deve ser documentada explicitamente** se o `arquiteto`/usuário decidir que não vale a pena simular isso (não é óbvio que valha o custo de engenharia — muitos scripts de gameplay não dependem dessa perda de precisão, mas ProfileStore/data managers que serializam CFrame podem).

## 9. Semântica de igualdade (`==`) e `FuzzyEq`

- **`FuzzyEq` epsilon default confirmado igual nos 3 tipos**: `0.00001` (`1e-5`), literal nos 3 YAMLs (`Vector3.yaml`, `Vector2.yaml`, `CFrame.yaml`).
- Vector2.FuzzyEq: comparação **por componente**, `epsilon` "must be a positive value no greater than 0.1" (única doc que menciona um teto para epsilon — Vector3/CFrame não mencionam teto).
- Vector3.FuzzyEq: descrito como "hybrid epsilon that scales relative to the magnitude of each component" — **diferente de Vector2**, que é `math.abs(diff) <= epsilon` puro por componente. Vector3 usa algo mais sofisticado (escalado pela magnitude), não um simples `abs(a-b) <= epsilon`. **Essa é uma diferença real de algoritmo entre Vector2.FuzzyEq e Vector3.FuzzyEq documentada na prosa oficial — não é a mesma fórmula.**
- CFrame.FuzzyEq: "similaridade de posição é component-wise, rotação usa uma aproximação rápida da diferença de ângulo" — terceiro algoritmo distinto, específico para CFrame.
- **`==` não documentado explicitamente para nenhum dos 3 tipos** nos YAMLs de datatype nem no `operators.md` genérico. **Não confirmado por citação direta** que `==` é comparação exata (sem epsilon) — é inferência forte (ver seção 5) baseada em: (a) a existência de `FuzzyEq` como método separado só faz sentido se `==` já não for fuzzy; (b) é comportamento amplamente relatado por devs Roblox em múltiplos threads do DevForum consultados (ex.: "Floating point errors when comparing 2 CFrames"), mas nenhum desses é uma declaração oficial formal da equipe Roblox encontrada nesta pesquisa.
